# PD 混部矩阵

混部指一个 vLLM 实例同时承担 prefill 和 decode。要回答的问题是：给定卡预算和序列，DP×TP 怎么切、并发开到多少，单卡输出最高。

## 1. 矩阵怎么列

卡数 N 下的合法布局是全部满足 `DP × TP = N` 的组合：

| 卡数 | 布局 |
|---|---|
| 1 | DP1-TP1 |
| 2 | DP2-TP1、DP1-TP2 |
| 4 | DP4-TP1、DP2-TP2、DP1-TP4 |
| 8 | DP8-TP1、DP4-TP2、DP2-TP4、DP1-TP8 |

每个布局 × 每条序列各自独立寻优，不要用一个布局的最优并发去跑另一个布局。一轮完整摸测的规模是 `布局数 × 序列数 × 搜索点数`，提前算出来再排期；本项目 49 个任务、158 个序列组合、555 次尝试。

卡预算不够全测时，优先级是：先把每个卡数的 DP 极端和 TP 极端跑出来（DP*N*-TP1 与 DP1-TP*N*），它们界定了范围，中间布局再填。

## 2. 并行方向的经验与它的边界

A5/950 上 Qwen3.8-27B 的实测（TPOT < 20ms，单位 tps/card）：

| 序列 | 1卡 | 2卡最优 | 4卡最优 | 8卡最优 |
|---|---|---|---|---|
| 4k/2k | 1260 (DP1-TP1, c28) | 1257 (DP2-TP1, c55) | 1273 (DP4-TP1, c112) | 1293 (DP8-TP1, c236) |
| 16k/1k | 334 (DP1-TP1, c8) | 318 (DP2-TP1, c16) | 308 (DP4-TP1, c34) | 310 (DP8-TP1, c69) |
| 64k/1k | 363 (DP1-TP1, c9) | 275 (DP1-TP2, c13) | 271 (DP2-TP2, c24) | 265 (DP4-TP2, c51) |
| 128k/1k | 177 (DP1-TP1, c5) | 145 (DP1-TP2, c7) | 152 (DP2-TP2, c16) | 98 (DP1-TP8, c18) |

从这张表读出三条，顺序不要颠倒：

1. **纯 DP 扩展近似保持单卡输出，TP 扩展显著降低单卡输出。** 4k/2k 上 DP8-TP1 是 1293，DP1-TP8 只有 317；4 卡上 DP4-TP1 是 1273，DP1-TP4 是 605。TP 的通信与切分开销直接吃掉单卡吞吐。
2. **单卡输出的上限基本在"最小卡数 + 最大 DP"处。** 加卡不会提高单卡输出，只会提高总吞吐和容量。所以"单卡输出寻优"的答案常常是单卡或纯 DP，多卡布局的意义在于能不能跑得下、TTFT 能不能达标。
3. **长序列才需要 TP，而且是被迫的。** 64k/128k 下单卡 KV cache 装不下足够并发，DP 分不出有效副本，TP 用来换显存和 TTFT。即使如此 2 卡的 DP1-TP2（275）仍低于 1 卡的 DP1-TP1（363）。

"短序列偏 DP、长序列偏 TP"这条经验只用来决定**先测哪个**，不用来跳过测量。4 卡 128k 上 DP2-TP2（152）反而高于 DP1-TP4（134），说明中间布局不能省。

## 3. 每个卡数的起手

| 卡数 | 先测 | 粗扫并发起点 |
|---|---|---|
| 1 | DP1-TP1 全部四条序列 | 2, 4, 8, 12, 16, 24, 32 |
| 2 | 短序列 DP2-TP1、长序列 DP1-TP2 | 4, 8, 16, 24, 32, 48 |
| 4 | DP4-TP1（短）、DP2-TP2（长），再补 DP1-TP4 | 24, 32, 48, 64, 80, 96 |
| 8 | DP8-TP1（短）、DP4-TP2（长），再补 DP2-TP4、DP1-TP8 | 48, 64, 96, 128, 192, 256 |

DP1-TP8 大概率不占优，但便宜，跑一遍把范围封住。

高 DP 下最优并发会很大：8 卡 DP8-TP1 的 4k/2k 最优并发是 236，总请求数 944。压测端的并发上限要相应放开，否则测到的是工具的上限不是服务的上限。

## 4. 多 DP 的三个坑

**前缀预热要逐域。** 多 DP 时请求被分到不同 DP 域，只预热一次只有一个域有缓存，整体命中率达不到 90%。用 `X-data-parallel-rank` 头逐域预热，保存每域的返回与耗时。

**命中率统计要按域取。** `config.py` 的 `POD_INFO` 填各 DP 域的 metrics 端口，否则只统计到主域。

**多 DP 与 MTP 子配置可能冲突。** 本项目在 PD 分离场景遇到原生多 DP 与 MTP 子配置冲突，改用多个独立 DP1 引擎组成逻辑 DP、由 proxy 分发。混部侧若遇到同类启动失败，先看是不是同一问题，不要当成布局不可行。

## 5. 显存先于并行

长序列的布局选择实际上是被显存决定的。拉起后用 block 数 × 128 token 反推可容纳请求数（见 [服务化基线](serving-baseline.md#5-显存与块数)），如果它已经小于你想测的并发，就不用测了，先换布局或换 KV cache 精度。

KV cache 精度的影响在长序列上非常直接：128k/1k 单卡，C8 包（`--kv-cache-dtype mxfp8`）能跑到并发 5、单卡输出 177，非 C8 包只能跑到并发 2、单卡输出 74。但两个权重包的差异不止 KV 精度，线性层的量化覆盖也不同（本项目统计：非 C8 包 256 个 `.weight` 标注 W8A8_MXFP8 且 `linear_attn.in_proj_qkv.weight` 等仍为 FLOAT，C8 包 504 个），所以这个差距不能全记到 C8 头上。拿到权重包先统计 `quant_model_description.json`，别从文件名推断。

## 6. 特性叠加的实测结论

以下是 2026-11、当前版本在 A5 上的现场结果，换版本重新核实：

| 特性 | 结论 | 证据 |
|---|---|---|
| GDN 优化算子（FLA AscendC 路径） | 默认已启用，是当前最优路径 | 切回 triton prefill 对照后单卡输出下降 0.7%–23%，16k/1k 上降幅最大 |
| Decode 捕获范围扩至 512 token | 对 TP4 这类最优并发接近 48 的布局有正收益 | 4 卡 DP1-TP4：4k/2k +6.0%（48→53 并发），16k/1k +3.7% |
| SP（PCP/DCP） | 当前版本不可用 | `platform.py` 在非 V2 runner 且 PCP>1 时显式拒绝；全部 PCP/DCP 布局启动失败（`server exited with code 1` 或端口 1200s 未就绪） |
| MM+RS / MM+AG 通算融合算子 | 当前版本不可用 | 调研结论，未进入矩阵 |

不可用的特性保留真实启动错误记 blocked，不写成吞吐 0 或"该布局不可行"。

捕获范围的收益只在最优并发原本卡在 `max(capture_sizes)/(k+1)` 附近时才出现。DP8-TP1 的最优并发 236 远高于 48，是因为每个 DP 域各自组批，域内批量才是入图的那个数。判断是否受限要看**单域批量**，不是系统并发。

## 7. 普通用例的命中污染会改变最优点

修掉普通用例的意外前缀命中（加 `cache_salt`）之后，1 卡 4k/2k 的最优点从并发 12 / 960 tps/card 变成并发 28 / 1260 tps/card。差异大到足以改变布局排序。

这意味着：发现命中口径有问题时，受影响的点必须重测，不能在表上做修正或加注释了事。本项目为此单独建了 `normal-zero-hit` 变体重跑，旧点保留但不进排名。

## 8. 混部的记录要点

布局名编码全部关键维度：`c8-n4-dp2-tp2-base` = C8 权重、4 卡、DP2-TP2、base 变体。变体名出现在尾部，便于对照表自动对齐。

每个布局目录保存 `job.json`（模型、卡、DP/TP、端口、用例、变体）、`serve-command.sh`、`serve-script-snapshot.sh`、`server.log`，每条序列一个 `in<输入>-out<输出>/search.json`。详见 [结果记录规范](result-recording.md)。
