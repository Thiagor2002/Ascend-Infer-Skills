# Ascend 单卡输出性能寻优

目标：在给定硬件预算（卡数）、给定定长序列场景、给定时延门限下，找到**满足门限的最大单卡输出吞吐**，并说明它由哪个并行布局、哪个并发、哪套特性开关得到。主指标永远是单卡输出吞吐 tps/card；TPOT、TTFT、prefix cache 命中率是硬门槛，不是可以交易的次要指标。

寻优不是调到一个好看的数就结束。一条结论必须同时带：服务化命令全文、AISBench 命令全文、请求级有效性证据、门限两侧的相邻并发点。缺任何一项，这条只能记为未验证。

本技能不绑定特定 agent，使用当前环境实际具备的文件读取、容器/SSH 与命令执行能力。没有真机时只做协议设计与静态核对，并标明未实测，不把文档步骤或估算写成实测结果。

## 先分型

| 形态 | 判据 | 入口 |
|---|---|---|
| 单实例混部 | 一个 vLLM 进程同时做 prefill 和 decode，卡全部归它 | [服务化基线](references/serving-baseline.md) → [并发寻优](references/concurrency-search.md) |
| PD 混部矩阵 | 要在 1/2/4/8 卡上比较 DP×TP 布局 | 先读混部矩阵参考（commit 2 引入） |
| PD 分离 | P、D 独立实例加 proxy，要做 RPS 配平 | 先读 PD 分离参考（commit 3 引入） |
| 多模态图文 | 输入含 image_url，TTFT 是主门限 | 先读多模态参考（commit 4 引入） |

同一次任务里不要混用形态的数据。混部的单卡吞吐按该实例的卡数归一；分离的按 P+D 全部卡数归一。

## 工作流

### 1. 固定口径

先把下面这些查清楚再动手，能从命令、日志、`pip show`、源码得到的不要问用户：

- 机型与可见卡：A5/950 或后续型号、`npu-smi info`、`ASCEND_RT_VISIBLE_DEVICES`、容器名；
- 软件指纹：vLLM commit、vLLM-Ascend commit、CANN、PTA、AISBench 版本、特性包版本（如 `flash-linear-attention-npu-a5`）；
- 权重包与量化覆盖：量化到哪些层由 `quant_model_description.json` 统计得出，不从文件名推断；
- base 特性栈与本轮唯一变量；
- 场景清单：每条是（输入长度、输出长度、prefix cache 目标命中率、TPOT 上限、TTFT 上限）；
- 卡预算，以及哪些卡正被别的任务占用。

两个权重包之间往往不止一个差异（KV cache 精度 + 线性层量化范围）。不能把两包的全部差距归因到包名里那一处标记。

### 2. 建立 base 服务并自检

按 [服务化基线](references/serving-baseline.md) 起服务。每个候选重启进程，不复用上一轮的 KV cache 与 prefix cache。拉起后先 `/v1/chat/completions` curl 通，再看 `/metrics`，最后才压测。启动失败、OOM、capture 失败记 blocked，不写成吞吐 0 或某个很差的数字。

**拉起即检查图捕获上限。** 投机解码下一个请求在 decode 步占 `num_speculative_tokens + 1` 个 token，捕获尺寸上限除以它才是能入图的请求数。并发越过这个值会掉出图模式回退 eager，TPOT 出现数倍突变，看起来像"到达硬件极限"，其实是配置边界。本项目 MTP3 + 上限 192 token 对应 48 并发，实测 48 并发 TPOT 12.7ms、52 并发 72.0ms。寻优前先算出这个值，并在报告里把它和实测拐点对齐。

### 3. 并发寻优

压测端配置与命令见 [AISBench 压测](references/aisbench-harness.md)，搜索策略见 [并发寻优协议](references/concurrency-search.md)：先粗扫定位门限跨越区间，再在区间内细扫到相邻并发，取满足门限的最高点。每个测点都要过请求级有效性校验才允许进入排名。

### 4. 叠加特性

base 跑通并拿到最优点后才叠加特性，一次一个变量，重新完整寻优。不同配置的最优并发不同，所以特性收益只能表述为"各自最优点的差值"，不能说成固定负载下的单算子加速比。

特性可用性以当前版本的真实启动结果为准。本项目 2026-11 的现场结论：SP 与 MM+RS/MM+AG 通算融合算子不可用；GDN 优化算子 `flash-linear-attention-npu-a5` 可用；PCP>1 在非 V2 runner 上被 `platform.py` 显式拒绝。这些是带时间戳的现场事实，不是平台常量，换版本后重新核实。

### 5. 建档与汇总

所有尝试建档，包括超限点和失败点。目录与文件约定见 [结果记录规范](references/result-recording.md)。最终产物是分组表格：混部按 1/2/4/8 卡分表，分离按 2/4/8 卡分表，每行标出该布局在门限内的最高单卡输出。

## 判断原则

- 并发是负载旋钮，`--request_rate 0` 闭环发送时并发唯一决定压力。总请求数固定为并发 × 4，让每个点的测量窗口可比。
- TPOT 随并发单调上升只是经验，不是保证。出现非单调或断崖时先查图捕获边界、显存块数、调度回退，不要直接当作噪声重测。
- 普通序列用例的 prefix cache 命中率必须为 0。同一数据源重复发送会意外命中，用每请求独立的 `cache_salt` 隔离。
- 长序列 90% 命中率是验收条件而不是副产品。预热要落在正式请求的公共前缀上，chat template 的额外 token 和 16-token 哈希边界都会让预热错位。实测命中率只接受 89.5%–90.5%。
- 结果表里的"平均输入"用服务端上报的实际值，不用目标长度，二者因 chat template 不等。
- `ignore_eos=True` 下的输出都是定长的，这类结果不能当精度证据。
- 多 DP 混部要逐 DP 域预热，否则部分域没有前缀，整体命中率不达标。
- 一个布局在短序列最优不代表长序列也最优。经验上短序列偏 DP、长序列偏 TP，但每条序列都要独立寻优。
- 不抢占他人正在运行的 NPU 任务，不 kill 不属于本轮的进程，不因为端口被占就批量清理。

## 交付

- 口径：机型、卡数、容器、两个 commit、AISBench 版本、权重包与量化覆盖、base 特性栈；
- 每个（布局 × 序列）一行：最优并发、TPOT、TTFT、E2E、输出吞吐、单卡输出吞吐、实测命中率、实际平均输入；
- 门限附近的相邻点，证明这是最高可行并发而不是随手一测；
- 有效性证据级别：请求成功数、输出长度一致性、流式时间戳、命中率复核；
- 未测、blocked、启动失败分别列出，不并入性能结论；
- 复现入口：每行对应的服务化脚本与 AISBench 命令路径。
